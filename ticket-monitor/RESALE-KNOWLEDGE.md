# 乃木坂46 リセール観測ナレッジ

`2nds watcher` で実際に観測したデータと、そこから分かったことをまとめる。
推測と観測を混ぜない。観測していないことは「観測していない」と書く。

最終更新: 2026-10-11（6期生ツアーのリセールは進行中）

## 2. 席種の法則（最も再現性が高い）

両イベントで同じ傾向が出た。**女性エリア・親子エリアは明らかに競争が緩い。**

### 真夏（神宮）

| 席種 | 掲載回数 | 中央値 |
|---|---|---|
| 親子・女性エリア | 35回 | **46秒** |
| 注釈付指定席 | 11回 | 29秒 |
| 見切れ席 | 17回 | 21秒 |
| バリアフリー席 | 2回 | 22秒 |
| 指定席 | 171回 | **12秒** |

### 6期生（Zepp）

| 席種 | 掲載回数 | 中央値 |
|---|---|---|
| 1Fスタンディング 女性エリア | 6回 | **10秒** |
| 2F指定席 | 9回 | 7秒 |
| 1Fスタンディング | 28回 | **5秒** |

**法則**: 女性エリアは一般席の 2〜4倍 長く残る。
一般席（神宮の指定席・Zeppの1Fスタンディング）が最も激戦で、最も数が多い。

**使い方**: 購入条件に合うなら女性エリアを狙う。一般席は数が多いぶん遭遇機会も多いが、
中央値5〜12秒なので「気づいてから操作する」余裕はほぼない。

## 5. 技術的な知見（みんなのチケット API）

### 使えるエンドポイント

```
GET https://api.nft.rakuten.co.jp/products/v0/mp/tickets/getTickets/{eventId}/{performance_start_on}
GET https://api.nft.rakuten.co.jp/products/v0/mp/tickets/getEventDates/{eventId}?limit=N
```

- **eventId `1004` は「乃木坂46」** であって特定のツアーではない
- 出品詳細ページ: `https://nft.rakuten.co.jp/moments/{RTK_id}/`
- 出品IDは `RTK_{unixtime}_{random}`。数字部分は**出品が作られた時刻**

`getTickets` の応答には公演の情報が全部入っている:

```json
{"id":40403,
 "performance_start_on":"2026-11-17T19:00:00",
 "performance_name":"（11/17(火)｜大阪）乃木坂46 6期生全国ツアー2026",
 "venue_name":"Zepp Osaka Bayside",
 "product_item_name":"1Fスタンディング",
 "symbol":"RTK_1791695328_vVqZDLeK",
 "resale_price":8800}
```

### 出品IDの時刻は「APIに出た時刻」ではない

出品ID `RTK_{unixtime}_{random}` の数字部分と、実際にAPIで見えた時刻の差を測った。

| | 6期生(n=38) | 真夏(n=182) |
|---|---|---|
| 最小 | **50秒** | **49秒** |
| 中央値 | 200秒 | 417秒 |

**49秒を下回る例が1件も無い。** 楽天側に固定の処理遅延があり、出品操作から
マーケットプレイスに現れるまで最低でも約50秒かかる。

**重要な含意**: 「掲載2秒」は *APIに現れてから消えるまで* の2秒である。
ポーリング間隔が0.25秒なら、気づいた時点で残り約1.75秒しかない。
**人の操作では取れない。** 速くできるのは検知までで、そこから先は人間の速度が壁になる。

### ⚠️ `getEventDates` は信用できない

**出品が実在しても公演を返さないことがある。** 2026-10-11 に確認:

- 14:54:15 に 11/17 の出品が実在し、その公演を明示指定していたプロセスは掴んだ
- 同時刻、`getEventDates` 依存の auto モードは公演を1つも得られなかった
- 14:57 に手で `curl` しても `{}`

**結論: 自動発見に頼らず、公演日時を明示して監視すること。**
一度も出品が出ていない公演（福岡など）は、そもそも auto では永久に登録されない。

### ⚠️ 存在しない日時でも 200 を返す

```
getTickets/1004/2026-11-17T19:00:00  → 200 {}   （実在する公演・出品ゼロ）
getTickets/1004/2026-11-17T03:00:00  → 200 {}   （存在しない公演）
```

**区別できない。** 日付×時刻の総当たりで公演を発見する方法は成立しない。

## 7. 運用で踏んだ地雷

| 事故 | 原因 | 対策 |
|---|---|---|
| 全出品が「対象外」になった | `new RegExp("")` は全てにマッチする。除外キーワードを空にすると全除外 | 空なら `/(?!)/`（何にもマッチしない）を返す `keywordPattern()` |
| CSVに同じ出品が二重記録 | 監視プロセスを5本同時に走らせていた | `watch-6ki.sh` が起動時に既存プロセスを落とす |
| 公演の9割を見ていなかった | `event-watcher` の引き継ぎは、その瞬間に出品がある公演しか掴まない | 全公演を明示指定 |
| 静かに監視が止まる | Macのスリープ、例外終了 | `caffeinate` ＋ 自動再起動（`watch-6ki.sh`） |
| 止まったことに気づかない | 出品ゼロと「見ていない」が画面上で同じ | 30回ごとに `N公演すべて0件` と能動的に報告 |

**共通する失敗の形**: 沈黙を「異常がない証拠」として読んでしまうこと。
「見ていて0件」と「そもそも見ていない」が区別できる表示にしておくこと。

## 8. この数字をどう使うか

- **中央値を「反応できる時間」だと思わないこと。** 6期生の中央値6秒は、
  通知に気づいてブラウザに切り替えるだけで消える長さ。
  検知したら**自動でページが開く**状態にしておかないと間に合わない
- **狙うなら女性エリア。** 一般席より2〜4倍長く残る（購入条件を満たす場合）
- **窓が開いた直後と締切直前に張ること。** 中間の時間帯は本当に何も出ない
- **初日公演のほうが出品が多い**（真夏 72% / 6期生も神奈川以外は同傾向）
- **購入条件を満たせない席種は通知から外す。** `EXCLUDE_KEYWORDS=女性` のように
  指定すると通知は止まるが、CSVへの記録は続く（記録は除外判定より前に行われる）。
  鳴っても買えない通知は、本命を取り逃がす原因にしかならない

### まだ分かっていないこと

- 6期生の夜間・締切日のデータ（10/13 23:59 まで観測中）
- アンダラの実態（45分しか観測できていない）
- 出品が消えた理由（売れたのか取り下げたのか）は API からは分からない
