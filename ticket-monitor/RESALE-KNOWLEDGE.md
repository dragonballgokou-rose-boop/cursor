**使い方**: 購入条件に合うなら女性エリアを狙う。一般席は数が多いぶん遭遇機会も多いが、
中央値5〜12秒なので「気づいてから操作する」余裕はほぼない。

## 5. 技術的な知見（みんなのチケット API）

### 使えるエンドポイント

```
GET https://api.nft.rakuten.co.jp/products/v0/mp/tickets/getTickets/{eventId}/{performance_start_on}
GET https://api.nft.rakuten.co.jp/products/v0/mp/tickets/getEventDates/{eventId}?limit=N
```

- **eventId `1004` は「乃木坂46」** であって特定のツアーではない
- 出品詳細ページ: `https://nft.rakuten.co.jp/moments/{RTK_id}/`
- 出品IDは `RTK_{unixtime}_{random}`。数字部分は**出品が作られた時刻**

`getTickets` の応答には公演の情報が全部入っている:

```json
{"id":40403,
 "performance_start_on":"2026-11-17T19:00:00",
 "performance_name":"（11/17(火)｜大阪）乃木坂46 6期生全国ツアー2026",
 "venue_name":"Zepp Osaka Bayside",
 "product_item_name":"1Fスタンディング",
 "symbol":"RTK_1791695328_vVqZDLeK",
 "resale_price":8800}
```

### 出品IDの時刻は「APIに出た時刻」ではない

出品ID `RTK_{unixtime}_{random}` の数字部分と、実際にAPIで見えた時刻の差を測った。

| | 6期生(n=38) | 真夏(n=182) |
|---|---|---|
| 最小 | **50秒** | **49秒** |
| 中央値 | 200秒 | 417秒 |

**49秒を下回る例が1件も無い。** 楽天側に固定の処理遅延があり、出品操作から
マーケットプレイスに現れるまで最低でも約50秒かかる。

**重要な含意**: 「掲載2秒」は *APIに現れてから消えるまで* の2秒である。
ポーリング間隔が0.25秒なら、気づいた時点で残り約1.75秒しかない。
**人の操作では取れない。** 速くできるのは検知までで、そこから先は人間の速度が壁になる。

### 「掲載2秒」の出品は、現れた時点ですでに売れている

> ⚠️ 2026-10-13 に取引履歴APIで再検証した結果、この節の解釈は修正が必要。
> 掲載2秒の出品は「既に売れている」のではなく「既に誰かのカートに入っている」。決済は出現の
> 17〜90秒後に成立している（最速8秒）。詳細は §9。以下は 10/11 時点の記述として残す。

2026-10-11、掲載2秒の出品で自動的に開いたページが **「売り切れ」** だった。
実地で確認した事実。

掲載時間の分布を見ると、6期生だけ **ちょうど2秒に突出したピーク**がある
（11件／3秒は1件のみ）。真夏にはこのピークが無い（2秒以下は1%）。
自然な分布ではなく、**キャッシュの残像**と考えるのが妥当。

出品操作からAPIに現れるまで最低50秒かかる（上記）。その伝播の間に売れてしまい、
キャッシュが追いつくまでの約2秒だけ「まだある」と表示され続けている。
真夏（神宮3万人）で起きなかったのは供給が多く即売れしなかったため。
6期生（Zepp 2,500人）は需要が供給を大きく超えている。

**幽霊の割合: 21%（12/57）。**

#### 出現時点では見分けられない

出品IDの時刻とAPIに現れた時刻の差（伝播の遅れ）で判別できないか試したが、
分布が重なっていて使えない。

| | n | 伝播の遅れ 中央値 |
|---|---|---|
| 幽霊（2秒以下） | 11 | 136秒 |
| 短命（3-9秒） | 18 | 351秒 |
| 本物（10秒以上） | 27 | 190秒 |

**通知を事前に止める手段は無い。** 5回に1回は「開いたら売り切れ」になる。
これは道具の不具合ではないので、そう覚悟して使う。

### 決済画面のURLは公演ごとだが、先回りはできない

```
https://nft.rakuten.co.jp/checkout/0/?tid=1004&ed=2026-12-01T19:00:00
                                      ^^^^^^^^ ^^^^^^^^^^^^^^^^^^^^^^
                                      イベントID  開演日時
```

公演ごとのURLにはなっているが、**カートに商品が無いと空のカート画面に
リダイレクトされる**。あらかじめこのタブを開いて待っても、⌘R でまた
空カートに飛ばされるだけで、ショートカットにはならない（実地で確認）。

**事前にできる準備は3つだけ**

1. 狙う出品ページをタブで開いておく（接続とセッションが暖まり、
   ボタンの位置も分かっている状態から始められる）
2. クレジットカードと住所を登録しておく。登録済みなら最終画面は
   「注文を確定する」ボタン1つだけで、入力画面は一切挟まらない
3. カートを空にしておく

検知後の経路（出品ページ → カートに入れる → 購入手続きへ → 注文を確定する）は
短縮できない。**人の操作速度がそのまま勝敗になる。**

### ⚠️ カートに入れても確保されない

カートに入れると出品一覧から消えるが、**それは確保ではない**。
同じ券を複数人がカートに持てて、**先に決済を完了した人が勝つ**。
実際に、カートに入れた福岡のチケットが別の人に決済されて「売り切れ」になった。

さらに、決済されなければその券は**一覧に戻ってくる**。
2026-10-11 の福岡の券 `RTK_1791715717_3Jroow4m` は 19:50:45 に出て2秒で消え、
**35秒後の 19:51:22 に同じIDで戻り**、また1秒で消えた。

**つまり「掲載2秒」は売れた時間ではなく、誰かがカートに入れるまでの時間。**
一度取られても諦める必要はない。保持者が決済しなければ必ず戻る。

### ⚠️ `getEventDates` は信用できない

**出品が実在しても公演を返さないことがある。** 2026-10-11 に確認:

- 14:54:15 に 11/17 の出品が実在し、その公演を明示指定していたプロセスは掴んだ
- 同時刻、`getEventDates` 依存の auto モードは公演を1つも得られなかった
- 14:57 に手で `curl` しても `{}`

**結論: 自動発見に頼らず、公演日時を明示して監視すること。**
一度も出品が出ていない公演（福岡など）は、そもそも auto では永久に登録されない。

### ⚠️ 存在しない日時でも 200 を返す

```
getTickets/1004/2026-11-17T19:00:00  → 200 {}   （実在する公演・出品ゼロ）
getTickets/1004/2026-11-17T03:00:00  → 200 {}   （存在しない公演）
```

**区別できない。** 日付×時刻の総当たりで公演を発見する方法は成立しない。

## 7. 運用で踏んだ地雷

| 事故 | 原因 | 対策 |
|---|---|---|
| 全出品が「対象外」になった | `new RegExp("")` は全てにマッチする。除外キーワードを空にすると全除外 | 空なら `/(?!)/`（何にもマッチしない）を返す `keywordPattern()` |
| CSVに同じ出品が二重記録 | 監視プロセスを5本同時に走らせていた | `watch-6ki.sh` が起動時に既存プロセスを落とす |
| 公演の9割を見ていなかった | `event-watcher` の引き継ぎは、その瞬間に出品がある公演しか掴まない | 全公演を明示指定 |
| 静かに監視が止まる | Macのスリープ、例外終了 | `caffeinate` ＋ 自動再起動（`watch-6ki.sh`） |
| 止まったことに気づかない | 出品ゼロと「見ていない」が画面上で同じ | 30回ごとに `N公演すべて0件` と能動的に報告 |

**共通する失敗の形**: 沈黙を「異常がない証拠」として読んでしまうこと。
「見ていて0件」と「そもそも見ていない」が区別できる表示にしておくこと。

## 8. この数字をどう使うか

- **中央値を「反応できる時間」だと思わないこと。** 6期生の中央値6秒は、
  通知に気づいてブラウザに切り替えるだけで消える長さ。
  検知したら**自動でページが開く**状態にしておかないと間に合わない
- **狙うなら女性エリア。** 一般席より2〜4倍長く残る（購入条件を満たす場合）
- **窓が開いた直後と締切直前に張ること。** 中間の時間帯は本当に何も出ない
- **初日公演のほうが出品が多い**（真夏 72% / 6期生も神奈川以外は同傾向）
- **購入条件を満たせない席種は通知から外す。** `EXCLUDE_KEYWORDS=女性` のように
  指定すると通知は止まるが、CSVへの記録は続く（記録は除外判定より前に行われる）。
  鳴っても買えない通知は、本命を取り逃がす原因にしかならない

### まだ分かっていないこと

- 6期生の夜間・締切日のデータ（10/13 23:59 まで観測中）
- アンダラの実態（45分しか観測できていない）
- 出品が消えた理由（売れたのか取り下げたのか）は API からは分からない

## 9. 2026-10-13 の追加計測 — 遅延の内訳と取引履歴

`trade-history.mjs` で全出品IDの取引履歴を取得し、CSV の出現時刻と突き合わせた。
図は `charts/ticket-flow.html`（イベント切替・表表示あり）。

### 取引履歴API（決済成立の時刻が分かる）

```
GET https://api.nft.rakuten.co.jp/products/v0/mp/marketplace/get-transaction-history?collectible_symbol={RTK_id}
→ {"history":[{"transactionType":"transfer","time":"2026-10-13T07:50:46.875000+09:00",
               "buyer_nick_name":"…","seller_nick_name":"…","price":8800}, {"transactionType":"issue",…}]}
```

- `transfer` = 売買成立（決済完了）。ミリ秒まで分かる。`issue` = 出品者へのトークン発行。
- 出品ID（RTK_）はトークンに紐づくので、買った人が再出品すると同じIDで別の transfer が増える（真夏で38件）。
- 取得は読むだけ。2並列・200ms間隔で334件を約1分。

### 「2秒で消える出品」の正体（6期生・270回の出現、10/13 08:27 時点）

| | 値 |
|---|---|
| 出現→決済成立（transfer）までの時間 | **中央値 47秒**（10%点 17秒 / 90%点 87秒）。3秒以内 0件、10秒以内 10件 |
| 決済に至らず消えた出現 | **105回 / 268回 = 39%**（カートに入ったまま戻った、または取り下げ） |
| 2秒以内に消えた出現（37回） | 決済成立 24回（最速8秒、多くは20〜60秒後）、未決済 13回。⚠️ 記録のみ（log）の公演は約2秒に1回しか見ていないので、その公演の「2秒」は「次の確認までに消えた」の意味。0.1秒で見ている狙い公演では 12/1 が 1/2、10/26 が 0/2 と n が小さい |
| 買い手の数 | 決済165件を **89人** が購入。上位10人で50件（30%）、最多でも8件 |

**結論: 2秒以内に消える出品は、出現から2秒以内に「カートに入れられて」いるが、決済はその後
人の速度（数十秒）で行われている。** 決済まで自動化した bot が独占している形ではない。
カート投入だけが異様に速い。考えられる説明は (a) カート投入までを自動化した利用者が複数いる、
(b) 出品ページを開いて待ち、再出現の瞬間に「カートに入れる」を押す人（戻り待ち）、の混在。
一覧ページに直接「カートに入れる」は無い（サイトのJSを確認。add_to_cart は出品詳細ページの1箇所のみ）。

出品ページで「売り切れ」と出たのは、売れたのではなく他人のカートに入っていた状態（stocks=0）。
決済されなければ戻ってくるので、**39% は待てば戻る**。

### 検知から人が操作を始めるまでの遅延（実測）

| 段 | 現状 | 根拠 |
|---|---|---|
| ポーリング（0.1秒間隔） | API出現→検知 平均 約77ms・最悪 約144ms | 周期は1周ぶんを差し引いて 100ms 固定（watch.log 実測 101.5ms）。1周 36ms（p50）/ 50ms（p99）。fetch 単発 22〜45ms、うちサーバー内処理 約20ms |
| API 自体 | 応答 22〜45ms（keep-alive 時） | `cache-control: no-store`、CDNキャッシュの兆候なし、HTTP/2 対応 |
| `open` でブラウザ起動 | 60〜80ms | `open -g` 実測 |
| 出品ページの表示（SSR） | **初回は 0.3秒 か 2.2秒**（2.2秒が 17〜50%）。同じURLの2回目以降は 0.3秒 | curl / Playwright で未訪問ID 16件を計測。ETag は毎回変わるのでHTML自体はキャッシュされていない |
| 読み上げ `say -v Kyoko` | 合成に 0.9〜1.5秒（短文でも1.2秒） | `say -o` 実測。音が出る前にこれだけかかる |
| 音声ファイル再生 `afplay` | 0.85秒（連続再生直後は 0.36秒） | オーディオデバイスの起床 0.5秒 ＋ 起動 0.35秒 |
| OS通知 `osascript` | 0.04秒 | 実測 |

**API のポーリングは既に限界に近い**（検知遅れは平均 0.08 秒。間隔を 0.05 秒にしても −26ms、応答が戻り次第再送しても −35ms が上限で、どう設計してもサーバー内処理 約25ms は残る。代わりにリクエスト率が 2〜3 倍になり、429 を一度でも受けると現行ロジックでは最短 48 秒〜最長 39 分間ポーリングが遅くなる）。残りの時間は
出品ページの初回表示（0.3〜2.2秒）と、音が鳴るまで（約1秒）、そして人の操作に消えている。
2秒以内にカートへ入れる相手に、新規出品で先んじるのは、ページが0.3秒で出た場合でも
検知0.1＋起動0.1＋表示0.4＋人の反応0.5〜1.0 = 1.1〜1.6秒 で、かなり分が悪い。
**勝ち筋は「戻り」**: 一度見た出品のページは2回目以降0.3秒で開き、タブに開いたままにできる。
39% は決済されずに戻るので、鳴ったら ⌘R →「カートに入れる」。
